## Current state
- `eval_checkpoint.py <ckpt>` evaluates one checkpoint over 5 seeds (0–4). Writes `evals/<YYYYmmddTHHMMSS>/episodes.csv` (seed, return, success, episode_len) and `log.txt` (`loaded <ckpt>`).
- Checkpoint step is only recoverable from `log.txt`; commit and dirty-tree state are not recorded.
- `tests/test_eval.py`: one pytest check, 5 seeds returned.
- Run while training continues, once per new checkpoint. On disk: 4 runs, ~5 rows each.

## Intent
Rank checkpoints by mean return and success rate, and see whether they're still improving as training goes. Asked by the researcher; exploration, not a gate. Metrics-first.

## Integration
- Form: script. `push_eval.py <run folder>` pushes one folder as a batch; also backfills existing folders. User wants the eval code touched as little as possible, and a failed upload must never break an eval, so `eval_checkpoint.py` does not import SignalFlag.
- structure-runs needed: yes. Run folders don't reliably record the checkpoint (`20260901T020000` has no `log.txt`). `eval_checkpoint.py` should write the checkpoint step next to `episodes.csv` (approved by user); that is its only change.
- Environment: separate venv for `push_eval.py` (e.g. `.venv-signalflag/`); repo has no dependency manager.
